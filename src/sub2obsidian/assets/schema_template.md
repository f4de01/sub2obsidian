# Schema

> 本文件源自 sub2obsidian 的 Schema 模板（版本 $schema_version），此后归本知识库所有，可随 Wiki 演进自行修改；工具不会覆盖它。这句里的版本号是 `sub2obsidian upgrade-schema` 判断要不要升级的依据，请保留。`CLAUDE.md` 与 `AGENTS.md` 内容相同，改一份时请同步另一份。

本知识库是一个 Karpathy 式 LLM Wiki：`sub2obsidian` 工具把用户在抖音、B站、公众号收藏的**来源**采集为**原始材料**；你（agent）按本 Schema 把原始材料**编译**成按**概念**组织、互相链接的 **Wiki**。用户只读 Wiki、在 Wiki 里写**批注**，并在「我的笔记」里写自己的思考。

用户在本目录对你说「编译」时，执行下文「编译流程」；说「填写筛选建议」（或「筛选」「给待筛清单写建议」）时，执行下文「筛选建议流程」；向你提问时，执行「问询流程」，问询之后说「存档」时，执行「存档流程」把回答存为综述页；说「体检」时，执行「全库体检流程」；说「合并 Schema」（或「升级 Schema」）时，执行「合并 Schema 流程」。

## 不可违反的规则

1. **原始材料只读**：不得修改、移动或删除 `$raw_dir/` 中的任何文件。来源状态只能通过 `sub2obsidian` 命令变更。
2. **我的笔记只读**：不得改动 `$notes_dir/` 中的任何文件；编译时把它作为**优先级最高的来源**读入（见「我的笔记」）。
3. **批注原样保留**：用户的批注（`> [!我]` callout）一个字都不能改、不能删，改写页面时随它所批注的内容一起移动（见「批注」）。你自己永远不写 `[!我]` callout。
4. **每条论断都有出处**：概念页与综述页中的每条论断都要带出处，指向对应的来源页；视频来源带时间戳（见「出处」）。没有出处的内容不得写进概念页与综述页。
5. **每次编译、存档、体检、合并 Schema 都以一次 git 提交结束**，提交说明按各流程规定的格式写。问询本身不写入任何文件，用户说「存档」才写。
6. **综述页不是证据**：概念页与来源页不得引用综述页作为出处。

## 知识库结构

| 位置 | 内容 | 谁来写 |
| --- | --- | --- |
| `$raw_dir/` | 原始材料：每个来源一个目录 | 只由 `sub2obsidian` 写入，只增不改 |
| `$sources_dir/` | 来源页：单个来源的摘要，作为概念页论断的证据 | agent |
| `$concepts_dir/` | 概念页：Wiki 的主产物，围绕一个知识概念汇总多个来源 | agent（用户只写批注） |
| `$domains_dir/` | 主题域入口页（如 AI、理财） | agent |
| `$syntheses_dir/` | 综述页：用户要求存档的问询答案，跨概念的比较或总结 | agent |
| `$notes_dir/` | 我的笔记：用户亲手写的思考 | 只有用户 |
| `$attachments_dir/` | 用户粘贴的附件 | 用户 |
| `index.md` | Wiki 页面索引 | agent |
| `log.md` | 操作日志，只追加 | agent |
| `$status_page` | Dataview 来源状态页 | `sub2obsidian` 初始化时写入，不要改 |
| `$screening_list` | 待筛清单：全部「待筛」来源的勾选清单 | `sub2obsidian sync` 生成；agent 只填「建议：」栏，勾选由用户完成 |
| `$pending_schema` | 待合并的新版 Schema，只在升级 Schema 时出现 | `sub2obsidian upgrade-schema` 写入；agent 按「合并 Schema 流程」合并后删除 |

Wiki 内部一律用 wikilink：`[[页面名]]`、`[[页面名#小节]]`、`[[页面名|显示文字]]`；指向平台原文用 Markdown 链接。页面名就是文件名（不含 `.md`），全库唯一。

## 原始材料

每个来源一个目录 `$raw_dir/<平台>/<平台内ID>/`，平台为 `bilibili`（B站）、`douyin`（抖音）、`wechat`（公众号）；页面与提交说明中一律写括号里的平台中文名：

- `元数据.md`：frontmatter 字段为 平台、平台内ID、规范链接、类型（视频/文章/图文）、标题、作者（UP主、公众号名等发布者）、署名（文章原文署名的作者，可空）、发布时间、时长（秒）、分P、视频标题（这两项见下文「B站 分P」）、采集途径（拉取/推送）、采集时间、来源状态、筛选建议（`sub2obsidian screen` 时从待筛清单的建议栏记入）、失败原因；正文为标题、封面与简介。
- `口播稿.md`（视频）：frontmatter 的「口播稿来源」注明来自平台字幕还是 ASR 转写；正文每段一行，以该段起始时刻 `[时:分:秒]` 开头。口播稿未经纠错，同音错字（如把「RAG」听成「rag」「瑞格」）按上下文理解，写进 Wiki 时用正确写法。
- `正文.md`（文章、图文）：标题下一行注明出处（公众号文章为公众号名、原文署名作者、发布时间与原文链接），之后是原文转成的 Markdown，图片以 `![](图01.png)` 引用同一目录中的图片文件；`封面.jpg` 等图片。

**B站 分P**：多P视频的每个分P是一条独立的来源。第 1 P 的平台内ID 就是 BV号（与单P视频相同），第 N P（N≥2）为 `BV号_pN`，规范链接带 `?p=N`。分P的标题为「视频标题 PN 分P标题」，时长、口播稿都只属于这一P；元数据的「分P」是分P序号、「视频标题」是整个视频的标题，单P视频这两项为空。同一视频的不同分P讲的是不同内容，各写各的来源页、各算一份证据，不是同内容版本。

**来源状态**：待筛、已拒绝、已通过、已采集、已转写、已编译、已失效。拉取来的收藏先以「待筛」登记、只有元数据；用户在待筛清单中勾选后执行 `sub2obsidian screen`，勾选的转为「已通过」、在下次 sync 时采集与转写，未勾选的转为「已拒绝」、只留元数据存根。推送来的来源直接为「已通过」。**已失效** = 在拿到可编译的原始材料之前，平台上已删除或不可见（如已采集、还没转写的视频，转写时下载不到音频），不能编译；已经拿到可编译的原始材料（文章与图文的正文、视频的口播稿）的来源，即使之后在平台上消失，也照常编译，不会变为已失效。**可编译** = 文章或图文「已采集」，或视频「已转写」。编译完成后由 `sub2obsidian mark-compiled` 转为「已编译」。

## 页面规范

### 来源页

一个来源一篇，放在 `$sources_dir/`。

- **页面名**：来源标题，去掉 `\ / : * ? " < > | # ^ [ ]` 等不能用于文件名或 wikilink 的字符，以及「【干货】」「建议收藏」之类与内容无关的修饰；超过 40 字时截短。与已有页面重名时在末尾加「（<平台中文名> <平台内ID>）」。
- **frontmatter**：

```yaml
---
页面类型: 来源页
平台: bilibili
平台内ID: BV1GJ411x7h7
规范链接: https://www.bilibili.com/video/BV1GJ411x7h7
来源类型: 视频            # 视频 / 文章 / 图文
作者: 某知识区UP主
发布时间: 2024-05-01      # 只写日期；元数据缺失时留空
时长: "10:12"            # 视频才有
原始材料: "[[$raw_dir/bilibili/BV1GJ411x7h7/元数据|原始材料]]"
主题域:
  - "[[AI]]"
概念:                    # 引用了本来源的概念页（含作为同内容版本被引用）
  - "[[RAG]]"
同内容版本: []            # 见「同内容版本」
编译时间: 2026-01-01
---
```

- **正文**结构：

```markdown
# <来源标题（原样）>

> [!info] B站 · 某知识区UP主 · 2024-05-01 · 10:12 · [原视频](https://www.bilibili.com/video/BV1GJ411x7h7)

## 摘要
三到五句话：这个来源讲了什么、结论是什么、适合谁看。

## 要点
- 按原始材料的顺序列出知识要点，视频每条带时间戳出处（B站 写跳转链接，抖音写时间戳文本）。
- 文章、图文：按原文的小节用三级标题分组（`### 小节名`），概念页即可用 `[[来源页#小节名]]` 精确引用；图中的知识按「读图规则」转写在对应小节里。

## 涉及的概念
- [[RAG]]：本来源对该概念贡献了什么（一句话）。

## 评价
可信度、时效性、局限、立场（如带货、营销号）、与其他来源的关系。没有可说的就省略本节。
```

### 概念页

Wiki 的主产物，放在 `$concepts_dir/`。

- **粒度**：一个**能独立讲清楚的概念**——能写出一段不依赖其他页面就成立的定义，且用户会单独查找它。只作为另一个概念的步骤或细节出现的内容，写进那个概念页的小节；某个小节被三个以上其他页面引用、或长到喧宾夺主时，再拆成独立概念页。工具、产品、方法论、指标都可以是概念；人物、公司一般不单独成页，除非来源围绕它讲了可复用的知识。
- **页面名（标题）**：用业界通用叫法——中文社区通用英文缩写的就用缩写（`RAG`、`MCP`），通用中文的就用中文（`提示词工程`）。其他叫法（中文全称、英文全称、常见别称、常见误写）全部写进 `aliases`，让任何一种叫法都能链到同一页。新建前先查 `index.md` 和全部概念页的 `aliases`，已有同义页面时并入，不得新建重复概念。
- **frontmatter**：

```yaml
---
页面类型: 概念页
aliases:
  - 检索增强生成
  - Retrieval-Augmented Generation
主题域:
  - "[[AI]]"
证据数: 2                # 独立证据的数量：同内容版本只算一份，我的笔记不计
创建时间: 2026-01-01
更新时间: 2026-01-01
---
```

- **正文**结构（小节顺序固定；没有内容的小节写「暂无」，「分歧」小节没有分歧时写「暂无分歧」）：

```markdown
# RAG

一句话定义（index.md 的摘要即取自这里）。

## 定义
用两三段话讲清楚它是什么、解决什么问题、核心机制。每条论断带出处。

## 要点
- 关键事实、原理、适用条件、常见误区。每条带出处。

## 实操与示例
- 怎么做、具体步骤、参数、命令、例子。每条带出处。

## 关系
- 上位：大语言模型应用
- 组成 / 依赖：[[向量数据库]]、Embedding
- 对比：微调——一句话说明区别
- 相关：长上下文

## 分歧
暂无分歧

## 出处
- [[来源页B]]（公众号 · 作者 · 2025-03-01）
- [[来源页A]]（B站 · 作者 · 2024-05-01）；同内容版本：[[来源页C]]（抖音）
- [[我的笔记/RAG 实践心得]]（我的笔记）
```

- **关系**：类型用 上位、下位、组成 / 依赖、被依赖、对比、相关、综述（讨论本概念的综述页）；对比写一句区别。关系本身是论断时（如「X 是 Y 的基础设施」）同样带出处。已有概念页的概念写成 wikilink；还没有概念页的概念写纯文本、不加链接，等它有了页面再改成链接（不要为了消灭纯文本去造只有一句话的空页面）。
- **出处小节**：列出本页引用过的全部来源页，按发布时间倒序；同一组同内容版本写在一行；我的笔记列在最后。
- **合并而不是追加**：新来源并入已有概念页时，把新知识揉进对应小节、与已有论断合并去重（合并后的论断保留所有出处），不要在页尾追加「来源 X 说……」段落。已有论断只有在被等价论断吸收时才可删去，且其出处要转移过去；与新说法冲突的旧论断不删，移入「分歧」。

### 主题域入口页

Wiki 的顶层划分，放在 `$domains_dir/<主题域>.md`。优先归入已有主题域；只有新概念明显不属于任何已有主题域时才新建，并在 `log.md` 中注明。

```markdown
---
页面类型: 主题域
aliases: []
---
# AI

一段话说明本主题域覆盖什么。

## 概念
按子主题分组列出本主题域的全部概念页，每个后面跟一句话定义。
- 检索与知识库：[[RAG]]——……；[[向量数据库]]——……

## 待裁决的分歧
- [[RAG#长上下文模型出现后，RAG 是否还有必要？]]：一句话描述争议点（链接到分歧的三级标题，同一页有多条分歧时才能区分）

## 综述
- [[RAG 与微调怎么选]]——一句话结论
```

没有内容的小节写「暂无」。

### 综述页

由用户说「存档」的问询答案沉淀而成（见「存档流程」），放在 `$syntheses_dir/`。综述页**跨多个概念**作比较或总结（「RAG 与微调怎么选」「入门 AI 编程的学习路线」）；只涉及一个概念、答案就在那个概念页里的问题不必存成综述页（见「存档流程」第 1 步）。

- **页面名**：概括问题的短语，不超过 20 字，用名词短语或「A 与 B 怎么选」式的问句，不带问号等不能用于文件名的字符。全库唯一。
- **frontmatter**：

```yaml
---
页面类型: 综述页
问题: 做企业内部知识库问答，该用 RAG 还是微调？   # 用户的原始问题，照抄
aliases: []
主题域:
  - "[[AI]]"
概念:                    # 本页比较或总结的概念页；只是顺带提到的不列
  - "[[RAG]]"
  - "[[微调]]"
证据数: 3                # 本页引用的独立证据数，计法同概念页
创建时间: 2026-01-01
更新时间: 2026-01-01
---
```

- **正文**结构（小节顺序固定）：

```markdown
# RAG 与微调怎么选

一句话结论（index.md 与主题域页的摘要即取自这里）。

## 结论
三到五条直接回答问题的结论。每条带出处。

## 分析
按比较维度或子问题分组（`### 维度`）；比较多个概念时先给一张对比表，表中每个单元格的论断带出处。

## 分歧与未知
- 结论依赖的待裁决分歧：[[RAG#长上下文模型出现后，RAG 是否还有必要？]]——一句话说明它如何影响结论
- Wiki 中缺乏证据、没能回答的部分，直接写明

## 相关概念
- [[RAG]]、[[微调]]、[[向量数据库]]

## 出处
- [[来源页B]]（公众号 · 作者 · 2025-03-01）
- [[来源页A]]（B站 · 作者 · 2024-05-01）；同内容版本：[[来源页C]]（抖音）
```

- **出处**：综述页同样**每条论断都要带出处**，格式与概念页完全相同（见「出处」），指向**来源页**（带时间戳）或我的笔记，而不是概念页：概念页只是二手汇总，写综述时把概念页论断后面的出处一并带过来。「出处」小节的写法与排序同概念页。
- 「分歧」照概念页的结论如实转述，不在综述页里替用户裁决；概念页里已裁决的分歧按裁决写，并注明依据。
- **综述页不是证据**：概念页与来源页不得把综述页当出处引用；综述页只引用来源页与我的笔记。
- 综述页被它的主题域入口页「综述」小节和 `index.md`「综述」小节链接；它讨论的概念页在「关系」中加一行 `- 综述：[[RAG 与微调怎么选]]`。

## 出处

概念页中每条论断后紧跟出处，放在全角括号里；多个出处用「；」分隔：

| 来源 | 出处写法 |
| --- | --- |
| B站 视频 | `（[[来源页]] [03:25](https://www.bilibili.com/video/BV1GJ411x7h7?p=1&t=205)）`：链接一律写成 `https://www.bilibili.com/video/<BV号>?p=<分P>&t=<秒数>`，BV号取平台内ID 中 `_p` 之前的部分，分P取元数据的「分P」（单P视频为 1），点击即跳到原视频这一P的该秒 |
| 抖音 视频 | `（[[来源页]] 03:25）`：抖音不支持时间戳跳转，只写时间戳文本 |
| 文章、图文 | `（[[来源页]]）`，能定位到来源页小节时写 `（[[来源页#小节]]）` |
| 我的笔记 | `（[[我的笔记/文件名]]）` |

- **时间戳**取口播稿中说出该论断的那一行开头的 `[时:分:秒]`：秒数 = 时×3600 + 分×60 + 秒；显示为 `分:秒`（满一小时为 `时:分:秒`）。例：`[00:03:25]` → `[03:25](…&t=205)`；`[01:02:05]` → `[1:02:05](…&t=3725)`。时间戳不得超出视频时长。
- 论断由多段口播支撑时，引用最能代表它的那一处；不要编造原始材料里没有的时间戳。
- 来源页「要点」中的条目同样带时间戳（此时可省略 `[[来源页]]` 本身）。

## 分歧

不同来源对同一问题说法冲突时（事实、数字、推荐做法相互矛盾，或说法随时间过时），不要自行裁决、不要悄悄覆盖旧说法，在概念页「分歧」小节并列保留各方说法：

```markdown
## 分歧

### 长上下文模型出现后，RAG 是否还有必要？
- **2025-03-01** 有必要，长上下文成本高、召回不稳定（[[来源页B]] [05:10](…&t=310)）
- **2024-05-01** 长上下文会取代 RAG（[[来源页A]] [02:00](…&t=120)）
- 状态：待裁决
```

- 每个争议点一个三级标题，写成一个问题；每种说法一行，以该来源的**发布时间**（元数据中的发布时间，取日期；缺失时用采集时间并注明）开头，**新说法在前**。
- 正文（定义、要点）中涉及争议的地方不选边，写明「说法不一，见 [[#分歧]]」。
- 我的笔记或批注表达了用户的判断时，把它作为一行写进分歧（以「我的笔记：」或「批注：」开头），状态改为「已裁决：……（依据我的笔记 / 批注）」，正文按用户的判断写；各方说法仍保留。这一行的日期：我的笔记取它最后一次提交的日期（`git log -1 --format=%cs -- <文件>`，未提交时取当天），批注取你第一次读到它的编译日期。
- 只是侧重点不同、可以同时成立的说法不算分歧，合并进正文即可。
- 只有一个来源的说法（包括对未来的预测，如「长上下文会取代 RAG」）不构成分歧：写进要点并注明发布日期，等另一个来源给出不同说法时再移入分歧。
- 新增或已裁决的分歧在主题域入口页的「待裁决的分歧」中同步。

## 批注

用户在概念页（及其他 Wiki 页面）里用 callout 写随手意见：

```markdown
> [!我] 实测 chunk 设成 500 字效果更好
> 第二行也属于这条批注
```

- 批注从 `> [!我]` 开始，到连续的 `>` 行结束；整块逐字保留，包括空格与换行。
- 批注紧跟在它所批注的段落或列表项之后。改写页面时，被批注的内容移到哪里，批注就跟到哪里；被批注的内容合并进别处时，批注跟到合并后的位置；实在无法判断时留在原小节末尾。任何情况下都不删除批注。
- 批注表达的意见优先级与我的笔记相同：批注指出某条论断有误或补充了经验时，相应调整正文（以批注为出处时写 `（批注）`），但批注本身不动。

## 我的笔记

- `$notes_dir/` 中的笔记是用户亲手写的思考与实践经验，是**优先级最高的来源**：与来源说法冲突时，正文以笔记为准，来源的说法记入「分歧」。
- 只读不写；不要求有固定格式。引用写 `（[[我的笔记/文件名]]）`。
- 每次编译都要读：与本批涉及概念相关的笔记（在 `$notes_dir/` 中搜索概念标题与 aliases），以及自上次编译以来新增或改动的笔记（`git log --since` 上次编译日期，或 `git status $notes_dir`）。

## 同内容版本

同一份内容在不同平台或以不同形式发布（跨平台搬运、文章版与视频版、同一作者的重发）对应多个来源，即**同内容版本**。

- **识别**：作者相同或注明转载，且标题相近、口播稿或正文高度重合。写来源页前先在 `index.md` 和 `$sources_dir/` 中查找同作者、相近标题的来源。
- **关联**：每个版本仍各写一篇来源页；在彼此 frontmatter 的 `同内容版本` 中互相列出（如 `同内容版本: ["[[来源页C]]"]`），并在「评价」中注明。
- **只算一份证据**：概念页引用时选一个代表版本（优先 B站 等可跳转时间戳的版本，其次发布最早的），其余写在同一出处后：`（[[来源页A]] [03:25](…&t=205)；同内容版本：[[来源页C]]）`。「出处」小节中同一组版本写在一行，`证据数` 只算一次。不同版本绝不能被当作「多方印证」。

## 读图规则

- 原始材料中的图片（文章配图、图文帖的图、带字的封面）要逐张看。图中的知识——幻灯片要点、表格、代码截图、流程与架构——**写成文字**：表格写成 Markdown 表格，代码写成代码块，流程写成有序列表，并带出处（`（[[来源页]] 图 3）`）。
- 只嵌入**关键示意图**：文字难以替代的架构图、流程图、对比图，每个概念页一般不超过两张。直接嵌入原始材料中的文件，不复制：`![[$raw_dir/wechat/<平台内ID>/图片名.png|600]]`，下一行写图注与出处。
- 装饰图、表情包、广告、二维码、普通封面不嵌入也不转述。

- 「综述」按创建日期倒序。

## 筛选建议流程

回填时 `sub2obsidian sync` 把拉取来的收藏以「待筛」登记（只有元数据，没有口播稿与正文），并生成或更新 `$screening_list`。清单按平台分组，每条来源的格式是：

```markdown
- [ ] <标题> `<平台>/<平台内ID>`
	- <作者> · <时长> · <发布日期> · [原链接](<规范链接>)
	- 简介：<简介摘要>
	- 建议：
```

B站 多P视频按视频分组：先是一行视频信息（不是来源，没有勾选框），其下每个分P一条来源，各有自己的勾选框与「建议：」，用户可以只保留其中几集：

```markdown
- 多P视频：<视频标题> · <作者> · <发布日期> · [原视频](<链接>)
	- 简介：<简介摘要>
	- [ ] P1 <分P标题> `bilibili/<BV号>`
		- <时长> · [原链接](<规范链接>)
		- 建议：
	- [ ] P2 <分P标题> `bilibili/<BV号>_p2`
		- <时长> · [原链接](<规范链接>)
		- 建议：
```

用户说「填写筛选建议」时，按顺序执行：

1. **读清单**：读 `$screening_list`，只处理「建议：」后面为空的来源（多P视频的每个分P各写一条建议，按分P标题判断，视频信息与简介是各分P共用的）；已有建议的不改，除非用户要求重填。清单里的信息不够判断时，读该来源的 `$raw_dir/<平台>/<平台内ID>/元数据.md`（完整简介）。只凭清单与元数据判断，不要联网查。
2. **判断是否知识类**：来源是否在讲可复用的知识——概念、原理、方法、工具用法、实操经验、行业与产品分析，都算**知识类**。娱乐、搞笑、音乐与 MV、影视剪辑、游戏实况、日常 vlog、带货与广告、纯新闻快讯、情绪向内容算**非知识类**。标题夸张但简介显示有干货的，算知识类；标题与简介都看不出内容的，写「待定」。
3. **建议主题域**：知识类的来源给出一个建议主题域。优先用已有的主题域（`index.md` 的「主题域」与 `$domains_dir/`）；都不合适时提一个新主题域名并标「（新）」，主题域是顶层划分（如 AI、理财），不要细到具体概念。
4. **写建议栏**：在该条「建议：」后面的同一行写，一条建议只占一行：
   - 知识类：`知识类 · <主题域> —— <一句话理由>`，如 `建议：知识类 · AI —— 讲 RAG 的原理与最小实现`；
   - 非知识类：`非知识类 —— <一句话理由>`，如 `建议：非知识类 —— 音乐 MV`；
   - 待定：`待定 —— <缺什么信息>`。

   只改「建议：」这一行：**不要勾选或取消勾选**（勾选由用户决定），不要改标题行与元数据行（行末的 `<平台>/<平台内ID>` 是 `sub2obsidian screen` 认来源的依据），不要增删条目，不要改动 `$raw_dir/`。
5. **汇报**：不提交 git（清单随下次 `sub2obsidian screen` 或 sync 一并提交），不记 `log.md`。向用户汇报：知识类多少条（按建议主题域分别计数）、非知识类多少条、待定多少条；然后提醒用户在 Obsidian 中勾选要保留的来源，再执行 `sub2obsidian screen`：勾选的转为「已通过」，下次 `sub2obsidian sync` 时采集并转写；未勾选的转为「已拒绝」，只留存根，不会再出现在清单里。建议栏会在 screen 时记入各来源元数据的「筛选建议」。

## 编译流程

用户说「编译」时，按顺序执行。所有 `sub2obsidian` 命令都在本知识库目录中执行并带上 `--vault .`。

1. **取可编译的来源**：执行 `sub2obsidian status --vault .`，读「可编译的来源」列表（每行开头的 `<平台>/<平台内ID>` 即来源目录 `$raw_dir/<平台>/<平台内ID>/`）。没有可编译的来源就告诉用户并结束。用户指定了范围就只编译那些；超过 10 个时分批，每批走完整流程、各自提交。同时执行 `git status --short`：Wiki 中未提交的改动多半是用户新写的批注，照常保留，随本次编译一起提交。
2. **写来源页**：逐个读来源目录中的 `元数据.md`、`口播稿.md` 或 `正文.md`、图片（按「读图规则」），先识别同内容版本，再按「来源页」规范写来源页。
3. **并入或新建概念页**：读 `index.md`、相关的已有概念页及我的笔记，确定本批来源涉及的概念；按「概念页」规范并入已有页面或新建页面，补全「关系」，处理「分歧」与「同内容版本」，更新 `证据数` 与 `更新时间`，并更新主题域入口页。
4. **更新 index 和 log**：按上文格式更新 `index.md`，在 `log.md` 末尾追加一条编译记录。
5. **轻量体检**：对本次新建或改写的页面逐项检查并修好：
   - 每条论断都有出处；出处中的来源页存在；时间戳与口播稿对得上、不超出时长，B站 链接的 `p=` 与来源的分P一致、`t=` 秒数与显示的时间一致；
   - wikilink 都能解析到已有页面（Obsidian 只按文件名解析，用别名显示时写 `[[页面名|别名]]`，不能写 `[[别名]]`），`[[页面#小节]]` 的小节确实存在（没有页面的概念写纯文本，见「关系」）；
   - 标题与 aliases 不与其他页面重复；没有新造出与已有概念同义的页面；
   - 分歧按日期新说法在前；同内容版本只算一份证据；
   - 本次新建的页面至少被主题域入口页或一个概念页链接（否则就是孤立页）；本批来源中以纯文本出现三次以上的概念，按「全库体检流程」中「缺失的概念页」判断是否建页；
   - 用 `git diff` 核对：原有的每个 `> [!我]` 批注块都原样还在；`$raw_dir/` 与 `$notes_dir/` 中没有任何文件被你改动。
6. **标记已编译**：执行 `sub2obsidian mark-compiled --vault . <平台>/<平台内ID> …`，列出本批全部来源。命令拒绝时（来源不可编译或写错），一个来源都不会被改动：按提示修正后重新执行，成功之前不要提交。
7. **git 提交**：只提交 Wiki、索引、日志与本批来源的元数据：

   ```
   git add -- Wiki index.md log.md $raw_dir/<平台>/<平台内ID>/元数据.md …
   git commit -F <提交说明文件>
   ```

   提交说明先写到系统临时目录中的文件（不要写进知识库），再用 `-F` 提交。格式（来源一行一个，写成「平台中文名 平台内ID 标题」，标题照抄元数据；概念页写页面名）：

   ```
   编译: 3 个来源

   来源:
   - B站 BV1GJ411x7h7 【大模型】RAG 到底是什么？10 分钟讲清楚
   - 公众号 3888064333_2247499360_1 RAG 已死？长上下文时代的检索
   新建概念页:
   - RAG
   - 向量数据库
   改写概念页:
   - 大语言模型
   ```

   提交后向用户简要汇报：编译了哪些来源，新建和改写了哪些概念页，新增了哪些待裁决的分歧。

## 问询流程

用户在本目录向你提问（「RAG 和微调怎么选？」「我收藏的内容里讲过哪些 Agent 框架？」），而不是要你编译、体检或填写筛选建议时，执行问询流程。问询**只读**：不写入任何文件——不改 Wiki、`index.md`、`log.md`，不提交 git——除非用户随后说「存档」（见「存档流程」）。

1. **先读 `index.md`**：从「主题域」「概念」「综述」三处定位相关页面；问题里的叫法不是页面名时，到概念页的 aliases 里找（`grep -rl "<叫法>" $concepts_dir`）。已有综述页回答过同一个问题时先读它，并在回答开头说明「Wiki 中已有综述 [[页面名]]（更新于 YYYY-MM-DD）」。
2. **读相关页面**：读相关的概念页（包括「分歧」小节）和主题域入口页；需要细节、原话或核对时间戳时，顺着出处读来源页，必要时读 `$raw_dir/` 中的口播稿与正文。与问题相关的我的笔记也要读，它的优先级最高。只用知识库里的内容回答，不要联网查。
3. **回答**：
   - 先给直接的结论，再展开；比较多个概念时用对比表。
   - 每条论断带出处，格式同「出处」：指向来源页，视频带时间戳（B站 写跳转链接），而不是只写概念页。这样存档时出处可以原样搬进综述页。
   - 涉及待裁决的分歧时，并列各方说法与日期，不替用户裁决，并链接 `[[概念页#分歧]]`；我的笔记或批注已经表态的，按它回答并注明依据。
   - Wiki 中没有或证据不足的部分，直说「Wiki 中没有相关内容」。可以用你自己的知识补充，但必须单独放在回答末尾，并标明「以下是 Wiki 之外的补充，没有出处」；这部分不会被存档。
4. **收尾**：回答跨两个以上概念、值得留存时，在末尾提示一句「说『存档』可以把这个回答存为综述页」。回答时发现的 Wiki 问题（断链、缺失的概念页、过时的说法）在末尾列出，建议用户发起体检；此时不要动手修。

## 存档流程

用户在问询之后说「存档」（或「存下来」「存成综述」）时，把**刚才的回答**（或用户指明的那一个回答）沉淀为综述页。会话里还没有可存档的回答时，请用户先提问。

1. **判断落点**：
   - 先查 `index.md` 的「综述」与 `$syntheses_dir/`：已有综述页回答同一个问题时，**改写那一页**（合并新内容，更新 `更新时间` 与 `证据数`），不要新建；
   - 回答只涉及一个概念、内容都已在那个概念页里时，告诉用户答案已在 `[[概念页]]` 中，无需另存；用户坚持时再存为综述页。
2. **写综述页**：按「综述页」规范写到 `$syntheses_dir/<页面名>.md`。从回答搬内容时逐条核对出处：引用的来源页存在，时间戳能在口播稿中找到。没有出处的论断（包括「Wiki 之外的补充」）不写进综述页；确实重要的，作为待查的问题写进「分歧与未知」。
3. **建立链接**：在主题域入口页的「综述」小节加一行；在本页讨论的每个概念页的「关系」小节加一行 `- 综述：[[页面名]]`。概念页的其他内容一律不动。
4. **更新 index 和 log**：在 `index.md` 的「综述」小节加一行 `- [[页面名]] —— 一句话结论（创建日期）`，按创建日期倒序；在 `log.md` 末尾追加一条存档记录（格式见「log.md」）。
5. **检查**：新页面的 wikilink 都能解析（见「全库体检流程」中的断链），`[[页面#小节]]` 的小节存在，出处格式正确。用 `git status --short` 与 `git diff` 核对：除了上述几处，你没有改动别的页面；`$raw_dir/` 与 `$notes_dir/` 没有被改动。存档前就有的未提交改动（多半是用户新写的批注）照常保留，一起提交。
6. **git 提交**：只提交 Wiki、索引与日志：

   ```
   git add -- Wiki index.md log.md
   git commit -F <提交说明文件>
   ```

   提交说明同样先写到系统临时目录中的文件，再用 `-F` 提交。格式（「综述页:」后写「新建」或「改写」）：

   ```
   存档: RAG 与微调怎么选

   问题: 做企业内部知识库问答，该用 RAG 还是微调？
   综述页: 新建
   涉及概念页:
   - RAG
   - 微调
   ```

   提交后告诉用户综述页的页面名与位置。

## 全库体检流程

用户说「体检」（或「全库体检」「检查一下 Wiki」）时执行。与编译时只看本次页面的轻量体检不同，全库体检检查 `Wiki/` 中的全部页面以及 `index.md`：找出并**修复**矛盾、孤立页、重复概念、断链、缺失的概念页，**列出**待裁决的分歧，并对本 Schema 提出改进建议，最后以一次 git 提交结束。体检不改动 `$raw_dir/`、`$notes_dir/` 与来源状态，不执行 `sub2obsidian mark-compiled`。

**几个定义**（Obsidian 只按文件名解析 wikilink，不按 aliases）：

- **断链**：wikilink（包括 `![[…]]` 嵌入和 frontmatter 里的链接）的目标不是知识库中任何文件的文件名（Markdown 文件不含 `.md`）或带目录的路径；`[[页面#小节]]` 中页面里没有该标题；`[[别名]]` 只与某页的 aliases 相同也算断链。`log.md` 只追加、不改写，旧记录里指向已改名或已合并页面的链接不算断链，不要修改。
- **孤立页**：除 `index.md` 和 `log.md` 外，没有任何其他 Wiki 页面（包括主题域入口页和 frontmatter 中的链接）链向它的概念页、来源页或综述页。
- **重复概念**：两个概念页讲的是同一个概念——一页的页面名是另一页的别称（中英文、全称与缩写、常见误写），aliases 有重叠，或定义实质相同。
- **矛盾**：未作为分歧记录的不一致——两个页面对同一事实说法不同；论断与它引用的来源页或原始材料不符（来源没这么说、时间戳对不上、B站 链接的 `p=` 与来源的分P不符或 `t=` 秒数与显示的时间不一致、超出时长）；综述页的结论与它讨论的概念页的现状不符；`证据数`、来源页的 `概念`、index 与主题域页的摘要和页面现状不符。
- **缺失的概念页**：没有页面、但已经以纯文本或断链在三个以上页面中出现的概念；或按「概念页」粒度规则应当拆出的小节（被三个以上其他页面引用、或长到喧宾夺主）。

按顺序执行：

1. **准备**：执行 `git status --short`，Wiki 中未提交的改动多半是用户新写的批注，照常保留，随本次体检一起提交。读 `index.md`；读 `log.md` 中最近的「体检」与「Schema」记录（`grep -n "^## \[.*\] \(体检\|Schema\)" log.md`），不要重提用户已经拒绝过的 Schema 改进建议。
2. **清点**：列出 `Wiki/` 下全部页面的页面名、页面类型与 aliases，以及每个页面发出的全部 wikilink（`grep -rnoE '!?\[\[[^]]+\]\]' Wiki index.md` 可以一次列出，表格中写作 `[[页面\|显示文字]]` 的竖线前有反斜杠）。页面多时可以写一个临时脚本来清点，脚本放在系统临时目录，不要写进知识库。
3. **逐类检查并修复**，按下面的顺序（先合并重复概念，因为它会改变链接目标）：
   1. **重复概念**：保留按「概念页」页面名规则应当作标题的那一页，把另一页按「合并而不是追加」并入：aliases 取并集并加入被并入页的页面名，论断合并去重、出处一并转移，分歧合并，重算 `证据数`，批注随它所批注的内容一起移过来。然后删除被并入的页面（`git rm`），把全库指向它的链接改成 `[[保留页|旧名]]`（`[[旧名#小节]]` 改指保留页中对应的小节），同步来源页的 `概念`、主题域入口页与 `index.md`。
   2. **断链**：目标是别名的，改成 `[[页面名|别名]]`；目标页改过名或被合并的，指向现名；小节不存在的，改指实际存在的小节，找不到对应小节就去掉 `#小节`；目标是还没有页面的概念的，先按下一条判断是否新建，不新建就改成纯文本；出处里的来源页不存在的，在 `$sources_dir/` 中按标题找回（可能改过名），找不到就核对原始材料，确认该来源已编译后补写来源页；嵌入的图片路径不存在的，在 `$raw_dir/` 中找回正确路径。
   3. **缺失的概念页**：来源页与原始材料中有足够的内容写出一段能独立成立的定义时，按「概念页」规范新建（每条论断带出处，只用知识库中已有的来源），把各页面中对它的纯文本提及改成链接，并加进主题域入口页与 `index.md`；材料不够时不建，列为遗留。
   4. **孤立页**：孤立的概念页加进它的主题域入口页「概念」小节，与其他概念之间有出处支持的关系时补进双方的「关系」；孤立的综述页加进主题域入口页「综述」小节和它讨论的概念页的「关系」；孤立的来源页说明它的知识没有进入概念层，按「编译流程」第 3 步把它的要点并入相关概念页（带出处）并更新它的 `概念`，确实没有可用的知识（如「评价」中判为营销号）时列为遗留并说明原因。
   5. **矛盾**：先回到双方引用的来源页和原始材料核对。一方转述错了来源的，改正这一方；来源本身说法不同的，在主概念页的「分歧」中按「分歧」规则记录（不要自行裁决），其他页面写「说法不一，见 [[概念页#分歧]]」；论断与出处不符的，按原始材料改正论断或出处，找不到依据的论断删去；综述页与概念页不符的，改写综述页的相应部分并更新它的 `更新时间`；元信息不符的，改正。
   6. **其余各项**：把「编译流程」第 5 步轻量体检的各项（每条论断都有出处、分歧新说法在前、同内容版本只算一份证据等）对全库检查一遍并修好。
4. **盘点分歧**：列出全部「状态：待裁决」的分歧（`grep -rn "状态：待裁决" $concepts_dir`）。用户已经在我的笔记或批注中表态、但仍标着待裁决的，按「分歧」规则改为已裁决；其余的不要替用户裁决。让每个主题域入口页的「待裁决的分歧」与概念页一致（补上缺的，去掉已裁决的）。
5. **Schema 改进建议**：根据本次体检的发现，对本 Schema 提出一到五条改进建议，比如反复出现的同类问题说明某条规则不清楚、Wiki 里已经形成而 Schema 没写的惯例、实际执行时互相矛盾或行不通的规则。每条写明：现象（举出具体页面）、改哪一节、改成什么（给出可以直接替换进 Schema 的文字）。没有值得提的就写「无」。**体检时不要修改 `CLAUDE.md` 与 `AGENTS.md`**：建议只写进 log 和给用户的汇报，是否采纳由用户决定。
6. **更新 index 和 log**：`index.md` 反映页面的增删与改名；在 `log.md` 末尾追加一条体检记录（格式见「log.md」），列出各类修复、遗留、待裁决的分歧数与 Schema 改进建议全文。
7. **核对**：用 `git diff` 与 `git status --short` 核对：原有的每个 `> [!我]` 批注块都原样还在（被合并的页面里的批注已经移到保留页）；`$raw_dir/` 与 `$notes_dir/` 中没有任何文件被你改动。
8. **git 提交**：没有发现问题时也要提交（只有 log 的记录）。

   ```
   git add -- Wiki index.md log.md
   git commit -F <提交说明文件>
   ```

   `git add -- Wiki` 同时记录被删除的页面。提交说明同样先写到系统临时目录中的文件，格式（每类一行一处，没有的写「无」；页面写页面名）：

   ```
   体检: 修复 4 处

   重复概念:
   - 向量库 并入 向量数据库
   断链:
   - RAG: [[检索增强]] 改为 [[RAG|检索增强]]
   孤立页:
   - 混合检索: 加入主题域 AI
   矛盾:
   - 无
   缺失的概念页:
   - 新建 Embedding
   已裁决的分歧:
   - RAG 切块多大合适？（依据批注）
   待裁决的分歧: 2 条
   Schema 改进建议: 1 条
   ```

9. **汇报**：向用户列出各类修复与遗留；逐条列出待裁决的分歧（争议点、各方说法与日期、所在页面），并说明裁决方式：在该分歧下写一条 `> [!我]` 批注或在我的笔记中写下判断，下次编译或体检时按「分歧」规则处理；最后给出编号的 Schema 改进建议，请用户逐条决定是否采纳。
10. **用户答复 Schema 改进建议后**：把采纳的建议改进 `CLAUDE.md` 与 `AGENTS.md`（两份保持一致），在 `log.md` 末尾追加一条 Schema 记录（采纳与未采纳的都列出），单独提交：`git add -- CLAUDE.md AGENTS.md log.md`，提交说明首行为 `Schema: <一句话摘要>`。一条都不采纳时只追加 log 记录并提交。

## 合并 Schema 流程

本 Schema 归知识库所有，会按采纳的体检建议和用户的要求演进，这些改动是知识库的**定制**；sub2obsidian 的 Schema 模板也会出新版本。工具从不覆盖本文件：`sub2obsidian upgrade-schema` 发现本文件开头说明中的版本号比模板旧时，在知识库根目录写出 `$pending_schema`——新版模板渲染出的完整 Schema（**待合并版本**），并单独提交。用户说「合并 Schema」（或「升级 Schema」）时，把待合并版本合并进 `CLAUDE.md` 与 `AGENTS.md`：保留定制，并入新模板的变化。按顺序执行：

1. **准备**：知识库根目录没有 `$pending_schema` 时，请用户先执行 `sub2obsidian upgrade-schema --vault .`，然后结束。读开头说明中的版本号：待合并版本的是**新版本**；`CLAUDE.md` 与 `AGENTS.md` 中较旧的一份是**当前版本**（开头说明被删改、找不到版本号的按旧版处理），与 `upgrade-schema` 的判断一致。新版本不高于当前版本时不合并：告诉用户待合并文件已过时，可以删除，然后结束。执行 `git status --short`：`CLAUDE.md` 或 `AGENTS.md` 有未提交的改动时，它们也算定制，照常保留、随本次合并一起提交。两份内容不一致时（`git diff --no-index -- CLAUDE.md AGENTS.md` 有输出），把差异告诉用户，按用户选定的那份作为当前 Schema。
2. **取模板原文**：当前 Schema 所基于的那一版模板，从 git 历史中取，存到系统临时目录（不要写进知识库）。本流程的命令在 Git Bash 中执行：Windows PowerShell 的 `>` 会把 `git show` 的输出存成 UTF-16，之后的 `git diff` 会把它当成二进制文件。
   - 合并过 Schema 的：最近一次合并的提交（`git log -1 --format=%h --grep="^Schema: 合并模板版本"`）删掉的待合并文件，即 `git show <提交>^:"$pending_schema"`；
   - 从未合并过的：初始化时写入的 `CLAUDE.md`，即 `git show <提交>:CLAUDE.md`，提交取 `git log --diff-filter=A --format=%h -- CLAUDE.md` 的最后一行（最早的一次）。
3. **列出定制与新模板的变化**：`git diff --no-index -- <模板原文> CLAUDE.md` 逐处列出**定制**；`git diff --no-index -- <模板原文> "$pending_schema"` 逐处列出**新模板的变化**。`log.md` 中的「Schema」记录（`grep -n "^## \[.*\] Schema" log.md`）说明了哪些定制是采纳的体检建议、为什么改。取不到模板原文时，逐节对比 `CLAUDE.md` 与待合并版本，拿不准某处是定制还是旧模板的写法时，问用户。
4. **合并**：以待合并版本为底稿，把每一处定制放回它在新版本中对应的位置：
   - 新模板没有动过的地方，定制原样放回；
   - 新版本已经包含了同样的改动（新模板吸收了同一条建议）的，不重复写；
   - 新模板改的恰好是定制改过的地方：两者能兼顾的，写成同时满足两者的文字；不能兼顾的，保留定制的写法，在汇报中列出，请用户决定；
   - 开头说明用待合并版本的，其中的版本号就是新版本；定制若改过开头说明的其他文字，照样放回，版本号仍写新版本。

   把结果写进 `CLAUDE.md`，再把 `AGENTS.md` 写成与它完全相同。
5. **核对**：对照第 3 步的两份清单，用 `git diff -- CLAUDE.md` 与 `git diff --no-index -- "$pending_schema" CLAUDE.md` 核对：每一处定制都还在；新模板的每一处变化都已并入（留给用户决定的除外）；开头说明中的版本号是新版本；`git diff --no-index -- CLAUDE.md AGENTS.md` 没有输出。合并 Schema 只改 `CLAUDE.md`、`AGENTS.md` 与 `log.md`：不改 Wiki 与 `index.md`，不改动 `$raw_dir/` 与 `$notes_dir/`。新版本的规范要求调整已有页面时，不要在本流程中改，在汇报中建议用户发起体检。
6. **记 log、删除待合并文件、git 提交**：在 `log.md` 末尾追加一条 Schema 记录（格式见「log.md」，摘要为「合并模板版本 <新版本>」），然后：

   ```
   git rm --quiet -- "$pending_schema"
   git add -- CLAUDE.md AGENTS.md log.md
   git commit -F <提交说明文件>
   ```

   提交说明同样先写到系统临时目录中的文件，首行固定为 `Schema: 合并模板版本 <新版本>`（下次合并时第 2 步靠它找到模板原文），格式（没有的写「无」）：

   ```
   Schema: 合并模板版本 5

   原版本: 4
   保留的定制:
   - 「出处」：采纳的体检建议 1（2026-01-04）
   并入的变化:
   - 新增「合并 Schema 流程」
   - 「原始材料」：已失效的说明
   待用户决定:
   - 无
   ```

7. **汇报**：告诉用户从哪个版本合并到了哪个版本，保留了哪些定制，并入了哪些变化；逐条列出留给用户决定的冲突（用户决定后按决定改 `CLAUDE.md` 与 `AGENTS.md`，追加一条 Schema 记录并单独提交，提交说明首行为 `Schema: <一句话摘要>`）；新版本要求调整已有页面时，建议用户发起体检。
